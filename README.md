# Shivaji Maharaj Sanstha Portal

A responsive React + TypeScript frontend prototype for a bilingual (Marathi/English) crowdfunding and information portal.

## Run locally

```bash
npm install
npm run dev
```

## Responsive site and PWA

The public site now shares one responsive layout across browser and installed-app views. Mobile navigation uses a keyboard-accessible drawer; the bottom donation bar is shown below 768px and is absent on the donation page. Both fundraising displays read the same `sansthaApi.getFundraisingSummary()` result. The existing API implementation is still `MockSansthaApi`, so its totals and the existing home-page journey stages remain demonstration content until the real data source is supplied.

Build and test the installed-app version locally:

```bash
npm run build
npm run preview -- --host 127.0.0.1 --port 4173
npx playwright test
```

For a new testing machine, run `npx playwright install chromium` first. The tests cover responsive overflow in both languages, drawer interaction, mocked payment verification success/failure, the gallery and offline caching. Mock payment tests never charge a card or create a real gateway order. Real-device iPhone Safari, Android installation and real Razorpay checkout still require device/account testing.

The service worker is enabled in production builds, not the Vite development server. It precaches build assets and an offline shell for public information routes. It has no runtime response cache: payment APIs, login APIs, third-party requests and all POSTs remain network-only. Direct offline navigation to `/donate` or `/admin` does not receive the cached application shell. If an already-open app navigates to Donate while offline, submission stops before making an order request. Updates require an explicit visitor action and the update control is hidden during checkout.

Installation is optional. The prompt appears only after 30 seconds plus scrolling, and dismissal suppresses it for seven days. iOS Safari receives Share → Add to Home Screen instructions. Production deployment must use HTTPS; a phone cannot install an app served over a plain HTTP LAN address. Icons are generated by `scripts/generate-icons.ps1` from a simple fort-and-flag mark.

Set `VITE_SITE_URL` to the deployed HTTPS origin before building to generate absolute canonical/Open Graph image URLs. The initial HTML has campaign-wide social metadata; route titles/canonicals update in the browser. Per-route previews for crawlers that do not execute JavaScript require server rendering or pre-rendered HTML from the deployment/backend. The social image is the attributed Raigad reference photo, not an approved rendering of the proposed monument.

The existing order and verification endpoints are retained. The form now includes a country entry in the existing order `notes` object. Only one-time payments are available: monthly subscriptions and official receipt downloads need backend support. A successful verified checkout shows its real gateway payment reference and client-recorded confirmation time, plus Web Share/copy-link support; it does not fabricate receipt numbers or tax documents.

For Docker builds, pass `VITE_SITE_URL` and `VITE_PAYMENT_API_BASE_URL` as build arguments. The payment base URL must be reachable from visitors' browsers; the original localhost default is for local development. Nginx serves `sw.js`, `index.html` and the manifest without immutable caching so future builds can be discovered.

## Included routes

- `/` — heritage-led public homepage and live fundraising progress
- `/donate` — donor amount, information, anonymous choice and gateway handoff UI
- `/project` — statue project overview and milestones
- `/transparency` — fundraising and utilization dashboard
- `/about`, `/activities` — public-content placeholders ready for the CMS API

## Backend integration

The contract and mock implementation are in `src/services/api.ts`. Swap `MockSansthaApi` for `HttpSansthaApi` when the Spring Boot API is available, and set `VITE_API_BASE_URL` if it is not served at `/api`.

Payment is intentionally not simulated: the UI creates an order but only a server-side gateway webhook can mark it as `SUCCESS` and issue a receipt.

## Razorpay UPI testing

Local development requires a Razorpay test key by default. Copy `.env.example` to `.env.local` to also enforce test mode in a build, then restart Vite after changing environment settings.

Configure the separate payment backend with the test key ID and matching test secret from your Razorpay dashboard. `/checkout/config` must return that public key ID, and `/orders` must create orders using the same credentials. Keep the secret on the backend; never put it in a `VITE_` variable. This repository contains only the frontend and cannot enable payment methods on your Razorpay account.

On `/donate`, complete the form and open checkout. If UPI ID entry is available, enter `success@razorpay` to test success or `failure@razorpay` to test failure. Real UPI app/Intent and QR payments require live-mode testing. If UPI is absent, confirm method availability with Razorpay; frontend settings cannot override account restrictions. Use another supported sandbox payment method in the meantime.

Successful checkout still calls `/payments/verify`; the backend must verify the signature before accepting payment. Test failures must not create successful donations or receipts. Close checkout to retry from the form.

For live payments, explicitly set `VITE_RAZORPAY_TEST_MODE=false` and configure matching live credentials on the backend. Setting this flag alone does not switch Razorpay modes.

Reference: [Razorpay test UPI details](https://razorpay.com/docs/payments/payments/test-upi-details/) and [Standard Checkout integration](https://razorpay.com/docs/payments/payment-gateway/web-integration/standard/integration-steps/).
